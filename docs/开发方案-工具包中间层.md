# 工具包中间层开发方案

> 状态：待评审
> 范围：纯开发方案文档，不含代码改动、不含发布。
> 落点：dsh-aiyayi 插件内独立子模块

## 1. 背景与目标

### 1.1 痛点

本体（阿依娅伊）经常需要调用"简单结果状态型"命令——例如查某个文件/目录在不在、读一个标志位、查某个依赖装没装、看当前目录、看 git 状态、查某个服务/端口通不通、看磁盘/内存占用等。这些命令输出短、一次性、失败重试意义不大、无需提炼。

当前的做法是派小伙伴（worker / retriever 检索员）跑一遍，把结果带回来。一来一回既耗 token 又耗时间——对一个本来只需要"看一眼就知道答案"的简单状态查询而言，成本不成比例。

真正值得派小伙伴的场景，是**数据量大、需要提炼/归纳/判断**的查询，例如检索大量文件、跨多个来源汇总、做综合分析等。

### 1.2 目标

做一个"工具包中间层"（以下简称中间层）：

- 本体可**异步调一批封装好的简单状态型工具**，无需派小伙伴。
- 鲁棒性、安全性、简单加工/判定逻辑**做在中间层**，由中间层统一收敛与加固。
- **分工原则**：简单状态型命令由中间层直接处理；工具本身不正常（报错、失效、行为异常）时，本体再派小伙伴去修复工具。即"能用中间层就跑中间层，中间层兜不住才派小伙伴"。

## 2. 架构设计

### 2.1 落点

- 放在 **dsh-aiyayi 插件内**，作为**独立子模块**实现：`lib/toolkit.js`。
- 通过 `package.json` 的 `exports` 字段暴露**子路径**（如 `dsh-aiyayi/lib/toolkit`），使外部可引用且不污染插件主入口。
- 通过 `cordis.patch.yml` 的**挂载声明**，把中间层挂到需要的 preset（preset-aiyayi 本体 / worker 小伙伴 / retriever 检索员——按需挂载，作用域天然隔离）。

### 2.2 工具分类：两类边界

| 类别 | 判定标准 | 处理方 |
| --- | --- | --- |
| **大量结果型** | 输出长、需提炼/归纳/判断、跨来源、需综合分析 | 派小伙伴 |
| **简单结果状态型** | 输出短、一次性、失败重试意义不大、不需提炼 | 中间层，本体可直接异步调用 |

边界定义要点：

- **看输出体量**：状态型工具的输出应当能在单次返回内给出明确结论（如 `true/false`、版本号、目录路径、标志位值）。
- **看是否需要提炼**：凡是"看完原始输出还要加工、判断、汇总"的，归大量结果型。
- **看失败语义**：失败重试意义不大（状态查询类错误通常是瞬时或确定性的，重试无收益）的，归状态型。

> 边界不是固定不变的：一个工具被证明输出稳定、结论明确后，可从小伙伴侧迁移到中间层；反之亦然。

### 2.3 中间层三要素

中间层内部维护三个核心能力：

1. **工具目录（Tool Registry）**：`名字 → { 定义, disposer, 底层映射 }`。
   - `定义`：工具对外暴露的接口（名称、参数、返回约定）。
   - `disposer`：由 `tools.register()` 返回的清理句柄，用于精确反注册。
   - `底层映射`：本中间层工具实际转发/委托到的底层实现（见第 5 节"转发边界"）。
2. **注册 / 反注册**：基于 DSH 官方原生支持的 `tools.register()`（返回 disposer）实现运行时动态注册；通过 disposer 做精确反注册。
3. **调用转发**：中间层封装壳把调用转发到底层真工具，可携带鲁棒/安全/判定逻辑后再返回本体。

## 3. 首批工具集规划（示例，可扩展）

筛选标准：**输出短 / 一次性 / 失败重试意义不大 / 不需提炼**。以下为候选方向，具体首批定哪些由后续讨论确认（见第 7 节）。

### 3.1 检查类

- 进程 / 服务在不在
- 端口通不通
- 文件 / 目录存不存在

### 3.2 状态类

- 读配置标志位
- 查记录文件最新一条
- 看磁盘 / 内存占用

### 3.3 确认类

- git 状态
- 当前目录
- 某依赖装没装

### 3.4 数据读取类（示例）

- 手表数据简单查询（如 SKG 手表的最近一次状态、标志位读取）——示例性质，具体范围待定。

## 4. 动态管理机制

### 4.1 精确反注册

- 利用 DSH 官方原生支持的 `tools.register()` 返回的 **disposer** 做精确反注册，避免注册泄漏。
- 中间层维护工具目录，对外提供 `add` / `remove` / `list` 三个操作：
  - `add(name, def, impl)`：注册一个新工具，登记目录并保存 disposer。
  - `remove(name)`：调用对应 disposer 反注册，并从目录移除。
  - `list()`：列出当前已注册的工具及状态。

### 4.2 作用域隔离

- 增删只对**挂载的 preset 作用域**生效，天然隔离：挂到哪个 preset，就在哪个 preset 内可见，不影响其他 preset 与全局。

### 4.3 自主增删的安全边界

- **策略层（可放开）**：决定**用哪些已注册工具、如何调整调用方式**（选工具、配参数、改调用策略）——这一层允许本体自主决策。
- **代码层（需外部验收）**：直接改插件代码、注册**新工具进系统**——这一层必须由外部验收，避免"既是改动者又是验收者"的跑偏风险（自己改完自己验收容易掩盖问题）。
- 一句话概括：**"用工具"可以自主，"造工具"需验收。**

## 5. 安全边界（分层表）

| 层 | 机制 | 说明 |
| --- | --- | --- |
| 白名单收敛 | `own-tools` + `restrict.js` | 复用 dsh-aiyayi 现有收敛机制：白名单放行，deny = 全集 − 白名单，未注册工具默认不可达。 |
| 前置判定 | `pre-execute`（deny / ask） | 在调用真正执行前注入鲁棒/安全/判定逻辑：可拒绝（deny）或先询问（ask）。 |
| 执行沙箱 | `dsh-permission-presets` | 底层工具在受权限约束的 preset 沙箱内执行，控制能力边界。 |
| 写操作确认 | `confirm` / `dryRun` | 对写类/有副作用操作：先 dryRun 预览或 confirm 确认，避免误写。 |
| 转发边界 | 只中间层持底层引用 | 底层真工具的引用只由中间层持有，本体/外部拿不到底层引用，只能通过中间层封装壳调用，防止绕过安全逻辑直连底层。 |

配套说明（复用 DSH 官方原生支持的注入点）：

- `pre-execute` / `execute` / `post-execute` 瀑布 + `result` 事件，用于调用前后注入鲁棒、安全、判定逻辑。
- `parent token` 嵌套转发：中间层封装壳可转发到底层真工具，同时保持调用链的 token 归属与审计可追溯。
